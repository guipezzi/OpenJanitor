# OpenJanitor — Project Plan

> **Status:** phase 0 done; phase 1 in progress ([§10](#phase-1--mvp-simple-clean)): the app can clean, with quarantine and the Protected list · **Last updated:** 2026-11-22
>
> This document is the source of truth for scope and design decisions. Change it through pull requests, like code.

## 1. Vision

OpenJanitor is a free, open source (GPLv3) desktop app that finds obsolete, temporary, and unnecessary files on Windows and helps people reclaim disk space **safely**.

Commercial cleaners usually lock their most useful features behind a paywall. OpenJanitor will never have one: every feature is free. GPLv3 makes sure nobody can take the code and ship it as a closed, paid product.

### Principles

1. **Safety first.** One wrong deletion destroys trust. When in doubt, the app doesn't touch the file.
2. **Transparency.** Every finding explains why it was flagged, which rule found it, and how risky it is.
3. **The user decides.** Scanning never deletes anything. Nothing is removed without an explicit action.
4. **Honesty.** No snake oil: no registry "optimization", no RAM boosters, no fake health scores.
5. **Attractive and approachable.** Simple by default, detailed on demand.
6. **Private.** Zero telemetry. The app works fully offline.

## 2. Scope

- **Platform:** Windows only. macOS and Linux are out of scope for now. OS-specific code is isolated in its own crate (`oj-windows`) so a future port stays possible.
- **Audience:** a middle ground. People who want a one-click cleanup, and power users who want to inspect every path.
- **Language:** English-native code, UI, docs, and commits. Portuguese (pt-BR) comes later; i18n keys exist from day one.

### Non-goals

- Registry cleaning (frees a few bytes, risks breaking the system)
- Clearing Prefetch (Windows rebuilds it, and boot is slower in the meantime)
- RAM "optimizers", SSD defragmentation, "PC health scores"
- Clearing cookies, history, or saved passwords by default (it logs the user out everywhere). May come later as opt-in privacy items.

## 4. Safety model

### 4.1 Scanning never deletes

Scanning is read-only. Files are only touched after the user selects findings and confirms.

### 4.2 Hard deny list

Hardcoded in `oj-safety`. No rule file can override it. The few exceptions inside system folders (for example `C:\Windows\Temp`) are also hardcoded in `oj-safety` and reviewed like code. Rule files can never add exceptions.

Always denied:

- Drive roots (`C:\`) and `%USERPROFILE%` itself
- `%WINDIR%`, except a hardcoded exception list. The initial list: `Temp`, `SoftwareDistribution\Download`, old files in `Logs`, `Minidump`, `LiveKernelReports`, `MEMORY.DMP`, and `Installer` (phase 2, special handling). It grows only through code review.
- The roots of `%ProgramFiles%`, `%ProgramFiles(x86)%`, and `%ProgramData%`. Their subfolders can only be flagged by the leftover detector (phase 2), and never when they belong to an installed program.
- User known folders: Desktop, Documents, Pictures, Music, Videos, and the OneDrive root. They're resolved with `SHGetKnownFolderPath`, because users can relocate them.
- Secrets and profile data: `.ssh`, `.gnupg`, credential stores, and browser profile files outside cache folders (`Cookies`, `Login Data`, `History`, and so on)
- `System Volume Information`, `$Recycle.Bin` (emptied through the shell API, never deleted by hand), `pagefile.sys`, `hiberfil.sys`, `swapfile.sys`
- OpenJanitor's own data and quarantine folders
- Other Windows installations (dual boot, old installs): on any drive other than the system drive, a `Windows\System32` folder at the root marks an installation. That drive's `Windows`, `Program Files`, `Program Files (x86)`, `ProgramData`, and `Users` folders are denied.

### 4.3 Traversal rules

- **Never follow reparse points** (junctions, symlinks, mount points). They're listed, never entered. Following a junction and deleting outside the target is a classic cleaner bug.
- **Skip cloud placeholders entirely** (OneDrive and Google Drive Files On-Demand). Deleting a placeholder can delete the file in the cloud, and reading its contents forces a download. Detect them by attributes (`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS` 0x400000, `FILE_ATTRIBUTE_RECALL_ON_OPEN` 0x40000, `FILE_ATTRIBUTE_OFFLINE` 0x1000) and by cloud reparse tags. The scan reads metadata only and never opens file contents.
- **Minimum age:** files modified more recently than the threshold are ignored, so in-progress installs aren't broken. Each rule declares its own (24 hours for temp files and caches, 30 days for old logs and shader caches). The Settings choice (24 hours, 3, 7, or 30 days) is a floor: a rule waits for whichever is longer, so the setting can make cleaning stricter but never shortens a rule's wait (D31). Advanced mode may add per-category overrides later.
- **Files in use** are skipped silently and reported as "in use" in the summary.
- **Hard links:** deleting a file that has more than one link frees no space. Its size only counts when the link count is 1. (This is also why WinSxS looks bigger than it really is.)
- **Size means size on disk** (allocated), not logical size, so compressed and sparse files don't inflate the "space freed" number.
- Only the selected drives are scanned. The system drive is selected by default, and other drives are opt-in ([§7.9](#79-drive-selection)). Network drives aren't supported.

### 4.4 Revalidation before acting

Things change between the scan and the action. Right before moving or deleting anything, `oj-safety` checks again that the path:

- still exists,
- is still not a reparse point or cloud placeholder,
- is not denied and not protected,
- still has the same size and modified time.

Anything that changed is skipped and reported.

**Empty folders.** After a cleanup removes the files in a folder, the folder itself is removed if it's now empty and lies inside one of the rule's locations. A rule's own location (such as `%TEMP%` itself) is never removed.

- Only folders that held a file the cleanup removed are candidates, deepest first, so a folder whose only content was emptied folders goes too.
- Each one goes through the same checks as a file: not denied, not protected, and still a plain folder (a junction put in its place is left alone).
- Windows only removes a folder that is empty at that moment, so a file created meanwhile keeps it. Folders that are a program's current directory can't be removed and are kept.
- Dry runs remove no folders, since their files are still there.

### 4.5 Quarantine

Flow: **Scan → Results (review) → Quarantine (restorable for N days) → Permanently deleted**

Default policy per risk level (all configurable):

| Risk                                   | Default action  | Retention |
| -------------------------------------- | --------------- | --------- |
| Low (temp files, regenerable caches)   | Delete directly | —         |
| Medium                                 | Quarantine      | 7 days    |
| Review (leftovers, Downloads)          | Quarantine      | 30 days   |

Settings can lengthen the retention (medium: 7, 14, or 30 days; review: 30, 60, or 90 days) but never shorten it, and medium and review files are never deleted directly (D31). For cautious users, "Always use the quarantine" sends low-risk files to quarantine too, for the medium retention; nothing is freed until they expire or the quarantine is emptied, and the Settings screen says so. Changes apply to the next cleanup; files already in quarantine keep their dates.

- **Quarantine doesn't free space until it's purged.** The UI shows both numbers, for example "Freed now: 5.5 GB · Will be freed on Dec 20: 3.9 GB", next to an "Empty quarantine now" button.
- **One quarantine folder per volume**, so moving a file is an instant rename instead of a slow copy across drives. Files are never copied: a move that would cross drives is refused.
  - **System drive, your files:** `%LOCALAPPDATA%\OpenJanitor\Quarantine\`. It's on the same volume, it's already private to the user, and it leaves no hidden folder at the drive root.
  - **System drive, system files:** `%PROGRAMDATA%\OpenJanitor\Quarantine\`, used by the elevated helper and changeable only by administrators (D22). If the helper used the personal folder, a program running as the user could edit a manifest or swap a stored file, and the helper would then restore it with admin rights. Restoring from here goes through the helper (one UAC prompt).
  - **Other drives:** `X:\.openjanitor\quarantine\`. The folder is hidden and its ACL is restricted to the user, plus SYSTEM and Administrators for items the helper moved.
- **Drives are identified by volume GUID** (`\\?\Volume{…}\`), not by drive letter, because letters can change when an external drive is reconnected. Each volume's quarantine keeps its own manifests, and the app keeps an index of all of them.
- **Disconnected drives:** their quarantined items show as "drive not connected" and can't be restored or purged until the drive is back. Expired items are purged the next time it's connected.
- **Unplugged mid-cleanup:** the operation stops. Each item's manifest entry is written before the item is moved, so everything already moved can still be restored.
- **FAT32 and exFAT drives** (common on USB sticks) have no ACLs, so their quarantine folder can't be restricted to the user. The UI says so when quarantining there.
- **Batches:** each cleanup that quarantines something creates a folder named after its date and time (UTC), holding `manifest.json` and the files under numbered names (`items/000001`, ...). Numbered names without extensions mean nothing in quarantine can be started by accident.
- **The manifest** (JSON, with a format version) records, for each item: its state, original path, size, allocated size, modified time, file ID, rule id, and when it was quarantined and expires. Permissions and timestamps aren't copied into it: a rename on the same volume keeps them on the file itself.
- **No content hash by default (D21).** Moving within a drive can't change the contents, and hashing means reading every byte (gigabytes for big caches). The stored file's identity is checked with size, modified time, and file ID instead. A BLAKE3 function exists in `oj-safety` for features that need one (checking a copy between drives, telling whether a restore conflict is the same file), and the manifest has an optional `hash` field.
- **Crash-safe:** each step is written to the manifest before it happens ("moving in", "restoring"), and the manifest itself is replaced atomically. At startup, recovery checks every unfinished step and finds the file at its original path or in the batch. A file is never in neither place.
- **Nothing in a manifest is trusted:** stored names must be exactly `items/` plus the item's number, restore destinations go through the deny list, and a stored file must still be the same file before it's restored or deleted.
- **In practice, most simple-clean items skip quarantine:** they're low risk, so the default policy deletes them directly. Quarantine is used for medium and review items, and for everything when "Always use the quarantine" is on.
- **Restore conflicts:** if something exists at the original path again, the user picks Replace, Keep both ("name (restored).ext"), or Skip. Replace moves the current file into quarantine first (for 30 days), so nothing is lost (D23). Missing parent folders are recreated. The choice is asked once per restore and applies to every conflict in it (D29).
- Expired items are purged when the app starts (and by scheduled cleaning, phase 4), after recovery and before the window can ask for anything. There's no prompt (D29): the dates were shown when the files went in, and the Quarantine screen says what was deleted. If the history file can't be opened, nothing is purged, so every deletion is on record. Unreadable batches are never touched. Expired items in the system quarantine need admin rights, so they wait for the next cleanup that already uses the helper, or for an "Empty (needs admin)" button; the app never shows a UAC prompt just for starting (D25).
- The Quarantine screen reuses the results tree component, with Restore and Delete now actions.

### 4.6 Privilege model

- The UI process always runs **unelevated**.
- `openjanitor-helper.exe` is a small, separate binary, started **on demand** with a UAC prompt, and only when the selection includes admin-only items. That's one prompt per cleanup, not one per file.
- The app is installed per machine, in Program Files (D18). A helper that lives in a folder the user can write to could be swapped by any program running as that user, and the next UAC prompt would elevate the swapped file.
- The helper **revalidates everything itself** (deny list, rules, [§4.4](#44-revalidation-before-acting)) and never trusts paths sent by the UI. Its IPC API is narrow: act on these findings from this rule set, create a restore point, run built-in action X.
- Why not "always run as admin":
  - A standard user who types an administrator's credentials runs the app as *that* account. `%TEMP%`, `AppData`, and browser caches then point to the wrong profile.
  - The UI is a webview. With admin rights, any UI bug becomes a system-level bug.
  - Windows blocks drag and drop from Explorer into elevated windows.
  - Elevating silently needs workarounds that are security holes themselves.
- **Later (phase 4):** the installer may offer "Install background service for admin tasks (no UAC prompts)". The service must verify its caller and revalidate everything the way the helper does before it ships.

### 4.7 System restore points

Restore points are created **only for advanced cleanups**, by the elevated helper, before any action runs.

- **System Protection is off on the system drive** → a popup explains that no restore point can be created. Files still go to quarantine, but system-level actions (DISM, Installer cleanup) can't be rolled back. Buttons: *Open System Protection settings* · *Continue without restore point* · *Cancel*. OpenJanitor never turns System Protection on by itself: it's a system setting, and the user's call.
- **A restore point was created less than 24h ago** → Windows allows one restore point every 24 hours by default (`SystemRestorePointCreationFrequency`), so no new one can be created. When the user starts another advanced clean in that window, a popup says: "A restore point was created on <date/time>. Windows only allows one every 24 hours, so this cleanup will rely on that one." Buttons: *Continue* · *Cancel*.
- Windows can skip creation silently, so the helper checks the newest restore point's timestamp before trying, and verifies afterward.
- Implementation: the WMI `SystemRestore` class (namespace `root\default`) for creating and listing restore points. OpenJanitor never changes the frequency setting.

### 4.8 Audit log

Every action is appended to a local log with timestamp, path, size, rule id, and result: delete, quarantine, restore, purge, restore point, and built-in action. The log is shown on the History screen and never leaves the machine.

- **File:** `%LOCALAPPDATA%\OpenJanitor\history.jsonl`, JSON Lines (D16). Each line has a `type` and a format version `v`.
- **A cleanup writes** one `file` line per file it acted on or skipped (with the reason), one `folder` line per folder it removed, and a final `cleanup` line with the totals. Its lines share a `cleanup` number.
- **The quarantine writes** a `quarantine` line per file, with its `action`: `restore`, `replace` (a file a restore moved aside), `delete` (on request), or `expired`. Each restore or delete ends with a `quarantine_totals` line, and its lines share an `action_id`.
- **Dry runs are logged too,** marked `"mode": "dry_run"`, so the History screen can tell them apart.
- If the log can't be opened, the cleanup doesn't start. If a write fails partway, the cleanup goes on (the quarantine manifests still record every move) and the summary says the history is incomplete.
- **Size and retention (D30):** about 300 bytes per file, so a 20,000-file cleanup adds about 6 MB. Per-file lines are kept for 90 days; after that, each cleanup or quarantine action keeps only its totals line (`cleanup` or `quarantine_totals`), which stays forever (the "total space freed" figure needs it).
- **Trimming** runs at startup, after expired quarantine files are deleted. Age is counted from when the cleanup or action started, so an entry never keeps half its files. Lines it can't read are never removed, and the file is rewritten atomically, and only when something goes.

## 5. Architecture

### 5.1 Repository layout

```
openjanitor/
├─ crates/
│  ├─ oj-core/      # scan engine, rule loading, findings
│  ├─ oj-safety/    # deny list, path validation, quarantine, deletion
│  │                #   (the only crate allowed to delete or move files)
│  ├─ oj-windows/   # Windows APIs: known folders, volumes, registry,
│  │                #   installed programs, restore points, file attributes
│  ├─ oj-helper/    # elevated helper binary
│  └─ oj-cli/       # command line (dev tool first, public later)
├─ src-tauri/       # Tauri app: IPC commands, app state
├─ ui/              # React + TypeScript + Tailwind CSS + shadcn/ui
├─ rules/           # TOML rule files, rule tests, locales/
├─ docs/
├─ package.json     # npm workspace root: Tauri CLI and UI scripts
└─ PLANNING.md
```

### 5.2 Data flow

```
Scan:    UI ──Tauri command──▶ src-tauri ──▶ oj-core (rules + traversal) ──▶ findings ──▶ UI

Clean:   UI ──Tauri command──▶ src-tauri ──▶ oj-safety (revalidate) ──▶ quarantine / delete
                                                  │
                                                  └─ admin-only items ──▶ oj-helper (UAC)
                                                                            └─▶ oj-safety (revalidate again)
```

The scan runs as a background task that emits progress events and can be cancelled.

### 5.3 Rule engine

Rules are **data only**. A rule file can't run commands or scripts. Special actions (DISM cleanup, emptying the Recycle Bin, Docker image pruning) are implemented in Rust and referenced by name. Community rule files can't add new ones.

```toml
[[rule]]
id          = "windows.temp.user"
category    = "temporary-files"
level       = "simple"          # simple | advanced
risk        = "low"             # low | medium | review
needs_admin = false
paths       = ["%TEMP%"]
include     = ["**/*"]
exclude     = []
min_age     = "24h"             # rule default; the user's setting can override
name        = "User temporary files"
description = "Files programs create while running. They're recreated when needed."

[[rule]]
id          = "windows.component-store"
category    = "windows-system"
level       = "advanced"
risk        = "medium"
needs_admin = true
builtin     = "dism-start-component-cleanup"
name        = "Windows component store cleanup"
description = "Removes superseded Windows components with DISM. Never deletes WinSxS files by hand."
```

- An optional `detect` field shows a rule only when its app exists (for example, Discord's folder).
- An optional `recommended = false` keeps a low-risk rule out of "Select recommended" (D24). Risk answers "can losing this hurt?"; `recommended` answers "should it be preselected?". Big caches that just grow back (graphics driver shader caches) are low risk but not recommended.
- An optional `app = { name = "Google Chrome", processes = ["chrome.exe"] }` names the program whose files the rule cleans. While any of those programs runs, the rule's files are left out of cleanups (D28). Process entries are plain program file names, never paths. Every browser and app cache rule must have one (a test checks).
- Every rule ships with a test: a fixture folder layout and the findings it should produce.
- Translations live in `rules/locales/<lang>.toml`, keyed by rule id.

### 5.4 Finding model

```rust
struct Finding {
    id: FindingId,
    rule_id: RuleId,
    category: Category,
    risk: Risk,              // Low | Medium | Review
    path: PathBuf,
    kind: Kind,              // File | Directory | Builtin
    size_on_disk: u64,
    file_count: u64,
    last_modified: SystemTime,
    needs_admin: bool,
    evidence: Vec<String>,   // human-readable reasons for the details panel
}
```

## 6. Cleaning scope

### 6.1 Simple clean (phase 1)

- User and system temp folders
- Recycle Bin, emptied through the shell API (D32):
  - One item per drive in the results (the system drive for now; other drives come with drive selection), with the item count and size Windows reports. That size is the deleted files' own size, a small exception to "size on disk".
  - Emptied as a whole, like File Explorer's *Empty Recycle Bin*, so the minimum age doesn't apply. That's why it's low risk but never preselected (`recommended = false`), and its details panel offers *Open the Recycle Bin* instead of *Open in Explorer*, to check or restore something first.
  - Only the signed-in user's Recycle Bin; other users' aren't touched, and no admin rights are needed.
  - The confirmation lists it under permanent deletion, with the D27 tick ("…and the 42 items in the Recycle Bin will be permanently deleted"). Right before emptying, `oj-safety` checks the item count and size again; if either changed since the scan, it's left alone, so nothing deleted after the scan goes with it (D26).
  - With "Always use the quarantine" on, it's left out of the plan and the confirmation says why: its contents can't be quarantined.
  - `$Recycle.Bin` stays on the deny list: it's never deleted by hand. The shell call lives alone in `oj-windows`, and only `oj-safety` may call it (a CI check enforces both).
  - The history gets one line per drive, with its item count and size.
- Browser caches for Chrome, Edge, Firefox, Brave, and Opera (cache only)
- Thumbnail cache
- Windows Error Reporting files and crash dumps
- Delivery Optimization cache
- Shader caches (DirectX, NVIDIA, AMD, Intel), only files untouched for 30 days. Games rebuild them on the next launch (sometimes for minutes), and the driver caches can reach many gigabytes, so NVIDIA, AMD, and Intel are low risk but not recommended: "Select recommended" leaves them out, and selected ones are deleted directly rather than held in quarantine (D24).
- App caches: Discord, Teams, Slack, VS Code. Spotify waits until its folders are checked on a real install: downloaded songs can share a folder with its cache.
- Old log files in `%WINDIR%\Logs` (30 days untouched, medium risk, so they go to quarantine by default)

The rules live in `rules/*.toml`; each one has a fixture test in `crates/oj-core/tests/fixtures.rs`.

Items that need admin rights show a shield icon and go through the helper.

If a browser or app whose cache is selected is still running, the app asks the user to close it first instead of silently skipping the files it has open (D28):

- Each browser and app rule names its program files (`chrome.exe`, `msedge.exe`, `ms-teams.exe`, ...). Only programs in the user's own Windows session count; other signed-in users' programs don't lock this user's caches.
- When the plan is built, the caches of running apps are left out. The confirmation names them ("Close this app to clean its cache · Google Chrome · 7,647 files · 420 MB") and offers *Check again*, which builds the plan again.
- Right before the cleanup starts, the check runs once more. Files of an app opened in between are skipped ("Its app was opened during the cleanup").
- OpenJanitor never closes apps itself: a closed app could lose unsaved work. Some apps (Edge, Teams, Discord) keep running in the notification area after their window closes, and the confirmation says so.
- If the list of running programs can't be read, the plan isn't built and the error is shown, rather than guessing that nothing is open.

### 6.2 Advanced clean (phase 2)

- Leftovers from uninstalled programs ([§6.3](#63-leftover-detection))
- `Windows.old`
- Windows Update download cache (`SoftwareDistribution\Download`), stopping and restarting the Windows Update service around it
- Component store cleanup with DISM `/StartComponentCleanup`. Never `/ResetBase` by default, because it makes installed updates impossible to uninstall.
- Developer caches: npm, pip, NuGet, Gradle, Maven, Cargo; `node_modules` and `target` folders in projects untouched for N months; Docker images (through the Docker CLI)
- Orphaned files in `C:\Windows\Installer` (risk: review)
- Old installers (`.exe`, `.msi`, `.zip`) in Downloads (risk: review, never preselected)
- Tips that change a setting instead of deleting files, such as shrinking the hibernation file with `powercfg -h off`. They're shown as suggestions, and applying one always asks first.

### 6.3 Leftover detection

1. **Inventory installed software:** `Uninstall` registry keys (HKLM, HKLM\WOW6432Node, HKCU), MSIX/AppX packages, winget/Scoop/Chocolatey lists, registered services.
2. **Collect candidate folders:** subfolders of `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%ProgramData%`, `%APPDATA%`, `%LOCALAPPDATA%`, and `AppData\LocalLow`, plus broken Start Menu shortcuts.
3. **Match** candidates against the inventory by name, publisher, and install path (fuzzy matching).
4. **Score** unmatched candidates and attach evidence, for example: "No installed program matches 'Adobe'. Last modified 3 years ago." Known shared folders (Microsoft, Common Files, Package Cache, and similar) are excluded through an allowlist.
5. Leftovers are always risk "review", never preselected, and quarantined for 30 days.

## 7. UX

### 7.1 Main screen

- **Drive selector** ([§7.9](#79-drive-selection)) next to the segmented drive usage bar (used space by category, cleanable, free; see [§7.8](#78-disk-usage-visualization))
- Three entry points: **Simple clean** · **Advanced clean** · **Space analysis**
- Results in a **grouped tree** (Category → Folder → Files), with tri-state checkboxes, sorted by size
- Each row shows a name, a risk badge (Low / Medium / Review), and a size, plus a shield icon when admin is needed
- **Nothing is preselected.** A "Select recommended" button selects low-risk items, except rules marked `recommended = false` (D24).
- **Details panel** on click: why the item was flagged, rule, evidence, last modified, "Open in Explorer" ("Open the Recycle Bin" for the Recycle Bin)
- Footer: selected count and total size, with **Protect** and **Clean** actions. The Clean label reflects the policy (delete or quarantine).
- Scan progress with a cancel button

**Cleaning** (D26, D27):

1. **Clean…** sends the selection (node ids, never paths) to Rust, which builds the plan: low risk is deleted, medium and review go to quarantine ([§4.5](#45-quarantine)).
2. **The confirmation** shows each group with its file count and size: "Deleted permanently", "Moved to quarantine for 7 days" (with the date they can be restored until), and "Left out" for items that need admin rights until the elevated helper exists. Caches of apps that are open are left out too, with a request to close them and *Check again* (D28). The button says what happens: *Delete permanently*, *Move to quarantine*, or *Delete and quarantine*.
3. **Permanent deletion needs a tick:** "I understand that N files will be permanently deleted" unlocks the button. Plans that only quarantine don't ask, since they can be undone.
4. **Old results:** if the scan is more than an hour old, the confirmation says so and offers *Scan again*. Nothing is recalculated behind the user's back.
5. **Progress** with *Stop*, which finishes the current file and then stops. One scan or cleanup runs at a time.
6. **Summary:** space freed now, what's in quarantine and until when, files left alone by reason (in use, changed since the scan, ...), folders removed, and files not touched after *Stop*. The old results are cleared; *Scan again* starts fresh.
7. **Dev builds run in dry-run mode** ([§9](#9-development-guardrails)), and the confirmation, progress, and summary say "Test mode".

### 7.2 Protected list

Items the user marks as false positives. Granularity: a file, a folder (recursive), a glob pattern (`*.psd`), or a whole rule. The list can be imported and exported as a file. Protected items never show up in results.

- **Patterns:** without a `\` or `/` they match file names anywhere (`*.psd`); with one, they match full paths (`D:\Projects\**`). Matching ignores case, like Windows.
- **Two layers:** the scanner leaves protected rules and files out, and the executor in `oj-safety` refuses them even if something asks it to act on one.
- **Protecting from the results** (a rule, a folder, or a file in the details panel) hides it at once and recomputes the totals, without a new scan and without losing the selection. Whole categories can't be protected; their rules can.
- **Storage:** `protected.json` in `%LOCALAPPDATA%\OpenJanitor`, saved atomically. If the file exists but can't be read, OpenJanitor refuses to scan or change anything and says why. A damaged list never counts as an empty one.
- **Import** adds entries and never removes any. **Export** saves a copy where the user picks. Both use the native Windows dialogs, opened from Rust; the UI gets no file access.
- Items the user stops protecting show up again on the next scan.

### 7.3 Quarantine screen

Uses the same tree component, with **Restore** and **Delete now** actions. It shows each item's expiry date, the total size held, and "Empty quarantine now".

- **Tree:** cleanup (named by its date, newest first) → the folder the files came from → file, with tri-state checkboxes and an "until <date>" column. Node ids come from a view of the manifests; actions quote the view's id, so a stale view can't act.
- **Top:** space held and file count, and the next files to go ("3 files (24 KB) will be deleted for good on Dec 1").
- **Restore** checks for conflicts first. If there are any, one dialog lists them and offers Replace, Keep both, or Skip for all of them (D29). Otherwise files go back right away.
- **Delete now** and **Empty quarantine now** confirm with the D27 tick.
- **Notes:** expired files deleted at startup, and batches that couldn't be read (left alone, with their folder).
- **One action at a time:** a restore or delete takes the same slot as a scan or a cleanup, so a cleanup can't write a manifest while a restore reads it.
- Dev builds show "Test mode" and only report what would happen.

### 7.4 Other screens

- **History:** the audit log and the total space freed ([§4.8](#48-audit-log)).
  - One entry per cleanup, restore, or delete, newest first, with what it freed, moved to quarantine, and left alone. Badges mark test runs, stopped cleanups, and interrupted ones (no totals line; numbers counted from their file lines).
  - Opening an entry loads its files, a page at a time, with each one's result and, for skipped files, the reason. Entries older than 90 days say their file details are gone (D30).
  - The total freed counts real cleanups and quarantine deletions only, never test runs.
  - Lines that can't be read are counted and shown as a warning, and left as they are.
- **Settings** (D31): one screen in three sections. Drives (PR 10), language (PR 12), and advanced mode (phase 2) join later.
  - **Cleaning:** the minimum file age (24 hours, 3, 7, or 30 days), a floor on every rule's own ([§4.3](#43-traversal-rules)). It applies from the next scan.
  - **Quarantine:** "Always use the quarantine" (off by default), and the retention for medium (7, 14, or 30 days) and review (30, 60, or 90 days) files ([§4.5](#45-quarantine)). It applies from the next cleanup.
  - **Appearance:** the theme (system, light, or dark). The window's title bar follows it too.
  - **Storage:** `settings.json` in `%LOCALAPPDATA%\OpenJanitor`, saved atomically, with a format version. Every change saves at once; there's no Save button. "Restore defaults" puts every setting back.
  - **A damaged file fails closed,** like the Protected list: scanning and cleaning refuse and say why, and the Settings screen offers "Restore defaults". Falling back to defaults silently could make the app less careful than the user chose (deleting what they asked to quarantine). Only the theme falls back, to the system's. Values outside the choices above count as damage too.

### 7.5 Progressive disclosure

The default view shows categories and plain-language descriptions. **Advanced mode** (a setting) adds full paths, rule ids, raw dates, and per-category minimum age. The first time someone uses Advanced clean, a one-time explanation appears.

### 7.6 Look and feel

Light and dark themes, following the Windows setting by default. Visual assets (icon, illustrations) are generated by the maintainer or taken from copyright-free sources, and their licenses are recorded in `docs/assets.md`.

### 7.7 Internationalization

Every UI string goes through `react-i18next` keys from the first commit, with only `en.json` at first. Rule names and descriptions are translated through `rules/locales/`. The pt-BR translation ships at the end of phase 1, once the phase 1 screens are stable (D20).

### 7.8 Disk usage visualization

Each view answers one question. They all show the same data, and the user can switch between them.

| View          | Question it answers                                               | Where                                   |
| ------------- | ----------------------------------------------------------------- | --------------------------------------- |
| Segmented bar | How full is the drive, and with what?                             | Top of the main screen, always visible  |
| Donut         | Which categories take the most space?                             | Space analysis landing view             |
| Sunburst      | What's inside each category? Clicking a segment drills into it.   | Alternative to the donut                |
| Treemap       | Where are the big folders and files?                              | Detail view                             |
| Sorted list   | Exact numbers, accessibility, actions                             | Always next to the chart                |

- **Pie/donut only for the top level**: at most ~6 categories plus "Other". Thin slices are unreadable, so folder-level detail goes to the sunburst and the treemap.
- **Linked selection:** selecting an item in a chart selects it in the list, and the other way around. A breadcrumb shows the current folder.
- **Categories by known location:** Windows, Programs, App data, Your files (known folders), System files (`pagefile.sys`, `hiberfil.sys`, restore points), and "Other and protected areas".
- **The chart always adds up to the real used space.** Areas that can't be read without admin rights (`System Volume Information`, other users' profiles) are computed as *volume used − measured* and shown as "Other and protected areas".
- **"Cleanable" is an overlay, not a slice.** A temp file is both "App data" and cleanable. After a scan, the cleanable part is highlighted inside its categories, and treemap tiles that contain findings get a marker.
- **Rust aggregates, the UI draws.** `oj-core` builds the folder-size tree. The UI receives only the largest N children per level (for example 50, plus "Other") and loads deeper levels on demand. Millions of nodes never reach the webview.
- **Progressive results:** the chart fills in while the scan runs, and the last result is cached so the view opens instantly. Fast scans that read the NTFS MFT are a phase 3 stretch goal.
- **Hard links are counted once** ([§4.3](#43-traversal-rules)), so WinSxS doesn't inflate the numbers.
- **Read-only at first.** Actions: Open in Explorer, Protect, Scan this folder for cleanable items. Deleting arbitrary user files from the chart is out of scope. If it's ever added, it goes through quarantine and the deny list like everything else.
- **Accessible:** colors come from a fixed categorical palette checked for color blindness, every chart has a legend, and the sorted list doubles as the table view.
- **Optional, later:** a before/after bar at the end of each cleanup, and a free-space-over-time line built from History.

### 7.9 Drive selection

- The app lists every volume with its letter, label, size, free space, file system, and type: **SSD or HDD**, and **internal or external (USB)**.
- **The system drive (where Windows is installed) is selected by default.** Other internal drives and external drives can be selected too, and the choice is remembered.
- Network and optical drives are shown as unsupported. BitLocker-locked drives are shown as locked and skipped.
- What the selection affects:
  - **Simple and advanced clean:** findings outside the selected drives are hidden. Most simple-clean locations (temp folders, caches) live on the system drive anyway.
  - **Search-based items** (developer caches, old installers, large files, duplicates) only search the selected drives.
  - **Space analysis:** one drive at a time, plus an overview with one bar per drive.
- External drives keep their quarantine on the drive itself and are identified by volume GUID ([§4.5](#45-quarantine)). Another Windows installation found on a drive is protected ([§4.2](#42-hard-deny-list)).
- Detection: `GetDriveTypeW` for the drive kind, and `IOCTL_STORAGE_QUERY_PROPERTY` for the bus type (USB drives often report themselves as "fixed") and the seek penalty (SSD vs. HDD).

## 8. Tech stack

| Layer         | Choice                                           |
| ------------- | ------------------------------------------------ |
| Core          | Rust (stable), Cargo workspace                   |
| Desktop shell | Tauri 2                                          |
| UI            | React, TypeScript, Vite, Tailwind CSS, shadcn/ui |
| Charts        | Apache ECharts (Apache-2.0, compatible with GPLv3) |
| i18n          | react-i18next                                    |
| Storage       | JSON files with `serde_json`; history as JSON Lines (D16) |
| Installer     | NSIS (Tauri bundler), per-machine install (D18)  |
| CI            | GitHub Actions on `windows-latest`               |

The app ships as Rust (all native work: scanning, aggregation, file operations) and TypeScript (the UI, including charts). No other runtime, such as Python, is bundled.

### 8.1 Alternatives considered

- **GPUI** (the native Rust UI framework from the Zed editor, with the gpui-kit component library), evaluated on 2026-11-21. It would give a lighter app and a single language, but scanning and cleaning speed would be the same, since that work is Rust either way. It was set aside because:
  - it's pre-1.0, with frequent breaking changes;
  - its documentation is thin ("read the Zed source code");
  - AI assistants know its API poorly, which is a real cost for an AI-assisted project;
  - treemap and sunburst charts would have to be drawn from scratch.

  The UI is a separate layer, so this can be revisited if a contributor wants to own a GPUI front end.

Candidate crates, to validate in phase 0: `windows` (Win32 APIs), `serde` + `toml` (rules), `jwalk` or `walkdir` (traversal), `globset` (patterns), `blake3` (hashes), `serde_json` (settings, history, and quarantine manifests), `thiserror` / `anyhow` (errors), `tracing` (logging), `tempfile` (tests).

## 9. Development guardrails

Most of the code will be AI-generated. These rules keep it safe:

1. **Only `oj-safety` may delete or move files.** CI fails if `remove_file`, `remove_dir`, `remove_dir_all`, `rename`, or the equivalent Win32 calls appear anywhere else. The UI gets no file system or shell access at all: no Tauri `fs` or `shell` plugin (the lockfiles are checked too, so one can't arrive as a dependency of another plugin), and its capabilities allow only `core:default`. It reaches the disk only through Rust commands in `src-tauri`.
2. **Tests never touch the real system.** They use temp directories and a fixture generator that builds fake profiles: temp files, junctions, read-only files, locked files, hard links.
3. **Dry-run mode (`OJ_DRY_RUN=1`)** makes every destructive operation log instead of act. Dev builds default to dry-run; turning it off is explicit.
4. **CI on every push:** `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, UI lint, typecheck and tests, and the check from item 1.
5. **Every rule has a test**, and every deny-list entry has a test proving it's blocked.
6. **English everywhere:** code, comments, commits, issues, docs.
7. **Small PRs.** Changes to `oj-safety` get extra review.

#### Phase 1 pull requests

Small PRs in four blocks. Each one leaves the app working. The Clean button only appears in block C, once quarantine and the Protected list exist and are tested; until then the app stays read-only.

**A. Show findings better (read-only)**

1. **Results model (Rust).** The last scan stays in app state, grouped as Category → Rule → Folder → Files. The UI loads one level at a time, so huge scans never reach the webview at once. Scan progress events and cancel.
2. **Results tree (UI).** Tri-state checkboxes, details panel, "Select recommended", footer with the selected count and size, and the sidebar for the app's screens.
3. **More rules.** Browser caches (Chrome, Edge, Firefox, Brave, Opera; cache folders only), shader caches (DirectX, NVIDIA, AMD), app caches (Discord, Spotify, Teams, Slack, VS Code), Windows Error Reporting files, and old log files, each with a fixture test. Can run alongside 1 and 2.

**B. Protect before deleting**

4. **Quarantine engine (`oj-safety`).** Move into the per-volume store with a manifest, restore with conflict choices, purge, and expiry. Engine and tests only, no UI.
5. **Protected list.** Files, folders, glob patterns, and whole rules, with import and export. The scanner hides protected items and the executor refuses them.

**C. Clean for real**

6. **Clean button.** A confirmation that shows what will be deleted and what will be quarantined, the per-risk policy, the audit log, and a results screen. The UI sends finding ids from the last scan, never paths. Dev builds stay in dry-run and say so on screen. Admin-only items are left out (and counted) until PR 11. Quarantine recovery runs at startup.
   - **6b. Running apps.** Before cleaning a browser or app cache, ask the user to close the app if it's running ([§6.1](#61-simple-clean-phase-1)), instead of skipping its open files. Rules name their apps' program files (`app`), and the plan leaves open apps out (D28).
7. **Quarantine and History screens**, and purging expired items at startup. Split in two:
   - **7a. Quarantine screen** ([§7.3](#73-quarantine-screen)): restore with conflict choices, delete now, empty, and deleting expired files at startup, all written to the history.
   - **7b. History screen** ([§7.4](#74-other-screens)): cleanups with their totals and files, the total space freed, and trimming old per-file lines (D30).
8. **Settings** ([§7.4](#74-other-screens)). Minimum age, quarantine policy and retention, "Always use the quarantine", and theme (system, light, dark), with D31's limits.
9. **Recycle Bin** through the shell API (D32): a builtin rule (`recycle-bin`), one result per drive, emptied as a whole after the same revalidation as files.

**D. Real Windows, then ship**

10. **Drives and charts.** Drive selector ([§7.9](#79-drive-selection)), the segmented drive bar, and the donut of cleanable space ([§7.8](#78-disk-usage-visualization)).
